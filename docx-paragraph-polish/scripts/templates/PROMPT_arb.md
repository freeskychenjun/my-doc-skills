## 输入
`{{ARB_IN_FILE}}` —— JSON 数组，每条形如：

```json
{
  "id": 123,
  "paraIndex": 456,
  "kind": "conflict",
  "original": "原文……",
  "candidates": ["第一遍改法……", "第二遍改法……"],
  "context": {"prev": {"id": 122, "text": "上一段摘要……"}, "next": {"id": 124, "text": "下一段摘要……"}},
  "flags": ["改写过程中提出的疑点……"],
  "lint": []
}
```

- `kind` = `conflict`（多个候选）或 `lowconf`（`candidates` 只有一条）。
- `context` 是**前后各 1 段的摘要**，用于判断本段是否与相邻段自相矛盾（可能为空对象）。

## 裁定口径（按顺序执行）

1. **标点体例不需要你操心**：半角括号→全角、`~`→`～`、半角引号→全角、文号去空格，父代理已有确定性脚本在写回前统一处理。**不要因为标点体例差异而选择某个候选**，只看文字表达。
2. **保持原意**：不得改变事实、不得新增原文没有的数据/原因/依据/结论/专业判断。
3. **数字、参数、年份、重现期、数值一律不得改动**。候选里若出现数字与 `original` 不一致的，**直接否决该候选**（保持 `original`）。
4. **单位幂次照抄原文**：不得把 `km2`→`km²`、`m3`→`m³`、`m2`→`m²`（原文上标多由 Word 字符格式实现，写成 Unicode 会造成双重上标）；也不得把原文的 `²`/`³` 改成普通数字。候选里若有这类改动，**否决该候选**。
5. **疑似事实错误**（数字与全文矛盾、年份/标准名明显不符、前后单位不一致、专名疑似窜入）：保持 `original` 原文不动，并在 `flag` 写明疑点。
6. **专名（地名、工程名、圩堤名、河流名、机构名、标准名）原则上保留**，不得替换。
7. **倾向最小改动**：改动最小的候选通常是纯纠错，最安全；方向改反的（把对的改成错的、或把「为」改成「是」这类）要否决。
8. **只有确实更好的表达才改**；可改可不改的，保持 `original`。
9. **段内自相矛盾可直接判定**：若候选修正的是本段自身即可断定的矛盾（如「由小至大排序」而所列数值用「＞」号、称「最高」但同段有更大值、序号重复、衍字使句意自相矛盾），可以采纳该修正——这类不需要外部证据。必要时结合 `context` 里前后段摘要判断。
