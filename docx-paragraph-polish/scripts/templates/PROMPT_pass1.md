## 输入（用 read 工具读，大文件可分次读）
- `{{PART_FILE}}` —— JSON 数组，元素形如 `{"id":1,"paraIndex":3,"text":"……"}`，`text` 为段落原文。

## 润色要求（只改字词表达，使表述更正式、规范、流畅）

1. 保持原意不变；**数字、参数、年份、重现期、水位、流量、面积等数值一律原样保留**，不得修改或替换。
2. 不规范的单位写法可以且应该改正（`Km/KM→km`、数字与单位之间多余空格等），改正时数值不变。
3. 地名、工程名、圩堤名、河流名、机构名、标准名等**专名原则上保留**，不得替换专名本身（专名内明显错字可改，但须在 `flag` 里留痕说明）。
4. **上标红线（特别强调）**：原文的单位幂次大多由 **Word 字符格式**实现（文本层是普通数字，显示出来就是 km²、m³/s）。**严禁把 `km2`→`km²`、`m3`→`m³`、`m2`→`m²`**（会造成「格式上标＋Unicode 上标」双重上标）；反过来，原文里已经是 Unicode 上标字符 `²`/`³` 的，**也必须原样保留，不得改成普通数字**。总之：**单位幂次一律按原文的字符写法照抄**。
   - 例外：原文写成 `m²/s` 而同一事项在报告中应为流量单位 `m³/s` 的，属事实疑点，**保持原文不动并写 flag**，不要自行改。
5. **标点体例**（全篇应统一，若发现漏网可顺手改正）：中文语境半角括号 `( )` → 全角 `（ ）`；数字区间半角 `~` → 全角 `～`；中文旁半角直引号 → 全角引号；文号内多余空格去掉。**纯公式/标准号语境**（如 `(4-31)`、`T=1.527(Bb'-10)`、`SL483-2017`）的半角符号保留。
6. **疑似事实错误不要改**：数字与全文矛盾、前后口径不一致、单位量纲明显错误、标准名称与年份不符等。做法是**不要改动该段文本**，并在 `flag` 写明疑点（一句话说清"哪里、疑似什么、建议核什么"）。
7. 不得新增原文没有的事实性内容（新数据、原因、依据、结论、专业判断）。
8. **禁止推测性补写**：原文有漏字/病句时，只做不改变语义的最小修补；无法确定原意的**不改动**，只写 `flag`。
9. 原文已足够规范时**不要改动该段**，不要为改而改。
10. 输出必须是**单个自然段的纯文本**：不得含换行符、列表符号、Markdown 标记；不得增删段落。
11. 只做字词级润色：**不改句序、不拆分或合并句子**。单段改动幅度尽量控制在 30% 以内。
12. 语言取正式书面语（"应""宜""应满足"等规范用语），避免口语化表达。

## 输出（瘦身契约 —— 只输出改动段与 flag 段，不抄原文）

输出文件 `{{OUT_FILE}}`（UTF-8 无 BOM）。结构是一个 JSON 对象，顶层恰好两个字段：`_meta` 与 `changes`。

- `_meta` 是**自检哨兵**，形如 `{"part": {{PART}}, "examined": <本片段落总数>, "changed": <与原文有差异的段数>, "lastId": <本片最后一个段落的 id>}`：
  - `part`：本分片号（就是 `{{PART}}`）；
  - `examined`：**本分片段落总数**（数一遍输入分片数组的长度再填，不得省略、不得乱填）；
  - `changed`：**与原文有差异的段数**（不是 `changes` 数组长度——只挂 flag 不改文的段不计入）；
  - `lastId`：**本分片最后一个段落的 id**（用来证明你确实读到了片尾）。
- `changes` 是数组，**只列出「改动过的段」与「有 flag 的段」**；其余段落一律不出现在输出里（原文父脚本自己会读，不需要你抄）：
  - 改动段：`{"id": 12, "newText": "<该段润色后的完整文本>"}`
  - 只提醒、不改动的段：`{"id": 40, "flag": "<一句话疑点说明>"}` —— **不要写 `newText`**
  - 既改动又需要提醒：`{"id": 40, "newText": "<该段润色后的完整文本>", "flag": "<一句话疑点说明>"}`
- **不要输出 `original`，不要输出 `paraIndex`**：父脚本的原文取自 `{{PART_FILE}}`，用不到这两个字段。
- **`newText` 与原文完全相同时，不要写这个字段**（想挂 flag 就只写 `id` + `flag`）。
- 本分片若确实无需改动、也没有 flag，就写：`{"_meta": {"part": {{PART}}, "examined": <本片段落总数>, "changed": 0, "lastId": <本片最后一个段落的 id>}, "changes": []}`。
- 写入 JSON 的字符串里不要用半角双引号，需要引号时用全角「」。
- 上面的 id / 数字 / 文本只是**字段形状示意**，把示例字符串照抄进 JSON 即判失败。

硬性纪律：

- **只有改动过的段落进 `changes`**：判据是改后文本与原文有差异；无差异又没有 flag 的段不得出现。
- `newText` 必须是**该段完整的润色结果**（不是 diff、不是片段），内不得出现换行符。
- `id` 必须取自 `{{PART_FILE}}`，不得手写、不得编造、不得遗漏任何改动段。
- 写文件前先核一遍 `_meta` 四个字段——这是唯一能证明「整片确实看过一遍」的凭据，不要因为省事跳过。
- 只写 `{{OUT_FILE}}` 这一个文件，不要修改任何输入文件。

## 两条硬纪律（踩过的坑，务必遵守）

1. **禁止同一文件多遍全文写入**：`{{OUT_FILE}}` 只允许 `write` **一次**。若首次写入被截断、JSON 不合法或 id 校验失败，**只能**用 `edit` 做 ≤3 次局部修补，**严禁再次 `write` 同一路径的全文**。写完在回复首行报 `WORDS=<changes 内容字符数>` 与 `IDS=<首尾 id>`，便于父代理与落盘文件核对。
   （理由：实测某分片把 ~37 k 字符的产物全文写了 3 次，该分片输出 token ×3、墙钟 ×2.5，还挤占同批次其它分片的端点吞吐。）
2. **路径照抄任务书，不得自创中间文件名**：只读 `{{PART_FILE}}` 与 `{{LINT_FILE}}`，只写 `{{OUT_FILE}}`。不得写 `part.json`、`out.json`、`result.json` 之类的中间文件，不得先写临时目录再搬运。

## 交付前自检（父代理会用 check_parts.py 机器复核，以下任一条不过即整片重跑）

- `_meta.examined` = 输入分片段落数；`_meta.lastId` = 输入最后一段 id；`_meta.part` = `{{PART}}`。
- 没有 `newText` 与原文完全相同的条目（相同就不要写 `newText`）。
- 没有抄错段（`newText` 与**本段**原文高度相似；若与别段原文几乎相同，会被判"串段"）。
- `newText` 的 `²`/`³` 个数不多于原文；数字多重集变化只告警，但请自查确实是必要改动。
