1 技能概述

报告智能校审（skill 标识：design-report-review）对一份水利工程设计报告执行逐条、可追溯的智能校审。它严格依照 references/检查要求.md 中定义的 8 大类 42 条检查要求，并按其「检查结果输出要求」产出校审报告：

  • 一一对应、不遗漏：42 条全部输出，即使某条全部符合也写出主要分析结论。
  • 引用完整要求原文：每条结论前附该条要求全文，便于读者将结论与要求对比。
  • 可追溯定位：每个结论与问题都标注文档中的定位（Word 页码 / 表号 / 题录），并精确照抄原文片段作为依据。
  • 默认输出 HTML：仪表板式（顶部横幅 + 左侧目录 + KPI 统计 + 问题筛选 + 行级配色表格）；用户明确要求 Markdown 时输出 Markdown。
设计要点： 确定性脚本负责抽取与机器可验证的硬证据（数值、引用对照、表格核算、编号顺序），并行 subagent 负责语义判断（条文落实、一致性、语法、合理性）。二者结合，既严谨又高效。

2 核心特性

🎯

逐条对应不遗漏

以 requirements.json 为序遍历全部 42 条，缺失项自动补查，确保全覆盖。

🤖

确定性 + 语义混合

数值/对照/编号交给脚本（零臆测），条文落实/一致性/语法交给语义判断（优先引用机器证据）。

⚡

并行高效

4 组 fan-out 并行 subagent（每组只读裁剪后切片 <2 万 token）+ 4 条纯规则脚本直出，墙钟提速 50~70%。

📍

精确可追溯

每条问题给出定位（第N页/表号）、原文照抄、问题类型与逐字修改建议。

📊

仪表板式报告

KPI 卡 + 筛选（全部/仅问题/仅不符合）+ 行级配色，浏览器直接打开、支持打印归档。

🔤

上下标正确渲染

m³/s、10⁸、km²、H₂O、SO₄ 等在 HTML 与 Markdown 中均正确显示。

🧮

表格自动核算

行/列合计、平均值、百分比、最大最小值逐项机器核算，异常只提示不误判。

🔁

规则可替换

references/ 下清单可替换为其他行业/版本，索引自动重建，便于移植。

4 工作原理

校审分为 6 个步骤：抽取 → 确定性证据 → 切片+直出 → 并行语义 → 收集润色 → 合成报告。前三步与最后一步为确定性脚本，中间为并行语义判断。

1
抽取

extract_docx.py / com_docx_extract.py：docx → 全文/表格/题录/引用/数值，重建合并单元格。

▶
2
确定性检查

deterministic_checks.py：表格核算、引用对照、有效数字、编号顺序 → det_*.json。

▶
2b
切片+直出

slice_artifacts.py 按4组裁剪产物；det_findings.py 直出 4 条结论（std_001/003/004、gram_007），不派 LLM。

▶
3
并行语义检查

4 组 subagent（A强条+常见/B一致性+表格/C语法+文字/D标准+法规）各读切片，墙钟≈最慢一组。

▶
4
收集+润色

collect_findings.py 合并（det 覆盖 subagent，42 条全覆盖）；polish_findings.py 去机器黑话。

▶
5
合成报告

assemble_report.py：逐条对应 + 引用原文 + 行级配色，默认 HTML，det 条目标注"（机器判定）"。

为什么是「确定性 + 语义」混合？

环节由谁负责负责什么原则
硬证据确定性脚本数值核算、引用有效性对照、有效数字、编号顺序宁可漏报（留给语义）也不误报
纯规则直出det_findings.pystd_001/003/004、gram_007 四条（数数/查表/加法）脚本比 LLM 更准，不经 subagent
语义判断并行 subagent（4 组）条文是否落实、前后一致性、语法合理性、规范合理性强制引用原文定位与机器证据，禁止臆测
合成assemble_report.py结构与引文来自脚本，结论与依据来自语义以 requirements.json 为序，逐条对应不遗漏
证据优先：凡 det_*.json 已给出的结论（如 std_003 流量有效数字、ds 标准有效性、gram_007 编号格式不一致），subagent 直接引用、不重复人工核算，避免误判。
提速要点：4 组并行（从原 7~8 组合并而来）+ 每组只读裁剪后切片（<2 万 token，而非全文 8 万 token）+ 4 条纯规则不经 LLM，整体墙钟提速 50~70%。

5 快速开始

最简单的用法：把本技能目录置于 .claude/skills/design-report-review/，然后在 Claude Code 对话中直接说：

用报告智能校审技能检查 安徽两湖涝区项建第2、3、5章.docx

Claude 会读取 SKILL.md 并自动执行抽取 → 确定性检查 → 并行语义检查 → 合成报告全流程。

输出位置

  • 默认（HTML）：在输入文档同目录生成 <文档名>_校审报告.html，浏览器直接打开。
  • 指定 Markdown：明确说"输出 Markdown"时生成 <文档名>_校审报告.md。

常用对话指令示例

你想做的事怎么说
默认 HTML 校审报告用报告智能校审检查 报告.docx
要 Markdown 版用报告智能校审检查 报告.docx，输出 Markdown
两种格式都要用报告智能校审检查 报告.docx，HTML 和 Markdown 都输出
带 Word 页码定位（需 Windows+Word）检查 报告.docx，并把段落定位转成 Word 页码
首次运行：若 scripts/references_index.json 或 scripts/requirements.json 缺失，Claude 会先自动运行 build_reference_index.py 与 parse_requirements.py 建索引，无需手动干预。
用其他 agent 平台？本技能默认面向 Claude Code。若想在 Codex / opencode / pi agent 上运行，参见 九、跨平台运行表现。

6 手动分步运行

便于调试、复现或单独调用某一环节。技能根目录记为 $SKILL。

0）建索引与解析要求（仅首次或清单更新后）

cd "$SKILL"
python scripts/maintain.py --force   # 一键重建 references_index.json + requirements.json

1）抽取 docx 为结构化 artifacts

python "$SKILL/scripts/extract_docx.py" "<docx或doc路径>" ["<输出目录>"]

默认输出到 $SKILL/_run/<文档名去后缀>/，生成 fulltext.md / tables.json / captions.json / citations.json / numbers.json / meta.json / locators.json。.doc 会自动尝试转换；若环境有数据安全软件（如 Agile DGS）拦截 Word 写盘导致转换文件被加密，改用 com_docx_extract.py 内存直读绕过。

1b）Word 页码定位（可选，需 Windows + Word）

python "$SKILL/scripts/page_map.py" "$SKILL/_run/<文档名>"

用 Word COM 计算每个段落对应的 Word 页码，回填 locators.json。无 Word 时跳过，定位自动回退为「章节标题§」。

2）确定性检查（机器可验证证据）

python "$SKILL/scripts/deterministic_checks.py" "$SKILL/_run/<文档名>"

产出四份 det_*.json 证据并打印摘要。这些证据是数值类、对照类检查的权威依据，语义 subagent 必须优先引用。流量有效数字按 SL/T 247 规范判定（整数末尾零不算有效数字）。

2b）按组切片 + 直出 4 条结论（提速提质核心）

python "$SKILL/scripts/slice_artifacts.py" "$SKILL/_run/<文档名>"   # 按4组裁剪 → _slices/groupA..D.json
python "$SKILL/scripts/det_findings.py" "$SKILL/_run/<文档名>"        # 直出 std_001/003/004、gram_007 四条

切片让每个 subagent 只读裁剪后的小文件（<2 万 token），而非全文；4 条纯规则条目由脚本直接出结论，不派 subagent。

3）并行语义检查（由 Claude fan-out 4 个 subagent）

一条消息内并发 4 个 subagent，每个只读对应切片，互不阻塞，墙钟≈最慢一组。各写 groupX.json。

组检查项条数读切片附 det 证据（已在切片内）
A强条 mp_001–011 + 常见 ci_*20groupA.jsondet_std003_brief
B一致性 cons_001–003 + 表格 tbl_001–0036groupB.jsondet_table_brief
C语法 gram_001–006/008 + 文字 std_0028groupC.jsondet_numbering、det_std004_grade
D标准 ds_001–002 + 法规 lr_001–0024groupD.jsondet_citations_brief
不派 subagent 的 4 条：std_001（大数单位）、std_003（流量有效数字）、std_004（等别级别）、gram_007（图表编号）——由 2b 步 det_findings.py 直接生成结论，在 4 步合并时并入。

4）收集 + 合并 + 校验

python "$SKILL/scripts/collect_findings.py" "$SKILL/_run/<文档名>"

收集 4 组 subagent 产物 + det_findings，det 覆盖同 id 的 subagent 结果，对照 requirements.json 确保 42 条全覆盖（缺失按"未检出"占位）。

4b）结论润色（去机器黑话）

python "$SKILL/scripts/polish_findings.py" "$SKILL/_run/<文档名>"

subagent 偶尔会把切片里的字段名（det_citations_brief.summary、consistency_issues=0、grid_omitted 等）照抄进结论。本脚本翻译成自然语言，并清理"本组切片"等暴露内部实现的措辞。必须在 collect 之后、assemble 之前运行。

5）合成报告

python "$SKILL/scripts/assemble_report.py" "$SKILL/_run/<文档名>"             # 默认 HTML
python "$SKILL/scripts/assemble_report.py" "$SKILL/_run/<文档名>" --format=md   # 只要 Markdown
python "$SKILL/scripts/assemble_report.py" "$SKILL/_run/<文档名>" --format=both # 两者都出

合成时内置 det 双保险（det_findings 覆盖优先），det 来源条目标注"（机器判定）"。

严格遵守 检查要求.md 的「检查结果输出要求」：与要求一一对应不遗漏、引用完整要求原文、即使符合也写主要分析结论。

报告由以下部分组成：

  • 顶部横幅：文档名、文件信息（段落数/表格数/检查项数）、校审依据。
  • 左侧目录：8 大类导航，滚动时自动高亮当前类别，点击平滑跳转。
  • KPI 统计卡：总数 / 符合 / 存在问题 / 符合率 / 不适用。
  • 问题筛选：全部 / 仅存在问题（部分符合+不符合）/ 仅不符合，一键过滤。
  • 按类别表格化结论：每条一行，列为「检查项 ｜ 要求 ｜ 检查结果 ｜ 说明 / 建议」。
  • 行级配色：符合（绿）/ 部分符合（橙）/ 不符合（红）/ 不适用（灰）；有问题行的检查结果与结论加粗、结论红色粗体。
  • 具体问题清单：对部分符合/不符合项，逐处列出 定位（第N页） → 原文照抄 → [问题类型] → 逐字修改建议。
  • 打印支持：@media print 已优化，隐藏侧栏与筛选条，保留配色，可直接打印归档。

Markdown 版（用户指定时）

按类别用二级/三级标题展开，每条含「要求（引用块）」「结论」「依据」，末尾附「校审结果汇总」表（类别 ｜ 条数 ｜ 符合 ｜ 部分符合 ｜ 不符合 ｜ 不适用）。在 GitHub / VSCode / Typora / Obsidian 等渲染器中正确显示。

上下标渲染

两种格式均正确渲染上下标：m3/s→m³/s、10的8次方→10⁸、km2/km²→km²、H2O→H₂O、SO4→SO₄。HTML 用 <sup>/<sub> 标签，Markdown 用 GFM 内联 <sup>/<sub> 标签。

groupA..D.json4 组 subagent 的结构化结论collect_findings 的输入
findings.json合并后的全部 42 条结论（含 det 直出 + subagent）合成报告的结论来源
关于 det_table 的 info：行平均、极值、多合计行/列等只给 info（机器核算供语义复核），不直接判错——是否成问题由 B 组 subagent 结合网格判定，避免 kW/台双单位、经验频率列等场景误报。

9 跨平台运行表现（pi agent / Codex / opencode）

本技能基于 Claude Code 的 SKILL.md 技能系统构建，依赖其自动加载技能、Agent/Workflow 并行 subagent等机制。换到 pi agent、OpenAI Codex CLI、opencode 等其他 agent 平台时，表现会有差异——但差异集中在「如何被触发、如何并行、由哪个模型下语义判断」，而确定性硬证据部分三家完全一致。

9.1 两层结构：哪些会变、哪些不变

层内容是否依赖具体平台
确定性层scripts/*.py（抽取、数值核算、引用对照、编号检查、报告合成）+ references_index.json / requirements.json不依赖 纯 Python + python-docx/lxml，三家跑出的 det_*.json 证据完全一致
编排 + 语义层SKILL.md 自动加载、Agent/Workflow 工具并行 fan-out 4 组 subagent、模型做条文落实/语法/合理性判断强依赖 这是三平台差异最大的部分
一句话结论：数值、引用、表格核算、编号等硬证据三家结果一样；语义判断的质量、并行速度、能否被自动触发会有明显差异。

9.2 四家平台逐项对比

9.3 实际影响（按优先级）

① 触发方式要改

在 Codex / opencode 里，「校审报告」这类词不会自动激活本技能。需把 SKILL.md 内容并进 AGENTS.md，或每次用 @SKILL.md 引用 / 把流程粘进 prompt。

② 并行退化为串行（变慢 3–5×）

效率核心是「一条消息内并发 4 组 subagent」。Codex 基本做不到等价 fan-out，会退化成 A→D 串行（SKILL.md 第 5 节本就写了这条降级路径，结果不变但变慢）；opencode 能配 subagent 但要手搓。

③ 语义判断质量随模型波动

强制性条文落实、排涝模数合理性、语法叠字等判断完全靠模型。换模型后，issues 清单的召回率与「宁缺毋滥、不编造」的把握度会变——这是最不可控的差异。

④ 确定性脚本零差异

deterministic_checks.py 产出的 det_*.json 三家一模一样，因为它们不经过模型——这是跨平台结果可对齐的锚点。

9.4 想在 Codex / opencode 上跑，怎么做

  1. 把 SKILL.md 转成 AGENTS.md（Codex / opencode 的通用约定），保留流程描述与脚本路径。
  2. 编排逻辑显式化：把「并发 4 组」改成明确的「依次跑这 4 个 prompt」，不依赖 Agent 工具。
  3. 以确定性层作为公共底座：无论哪个平台，先跑 extract_docx.py + deterministic_checks.py + det_findings.py 拿到 det_*.json 与 4 条直出结论，再让模型只做语义层——这样跨平台结果最稳定。
跨平台一致性建议：若需多平台结果可对齐，以 det_*.json 为准绳——它们在任何平台都相同。语义层结论出现分歧时，以确定性证据为准。

11 清单动态维护

三份参考清单（检查要求.md / 水利标准.md / 法律法规.md）是校审的权威源，可由用户随时发起维护——新增、删除、改写条目，或更新标准的现行有效版本。改完 .md 跑一下重建脚本即生效，无需改代码。

10.1 重建命令速查（每次维护后必跑）

改了哪个 .md要跑的重建脚本重新生成的 JSON
检查要求.mdpython scripts/parse_requirements.pyrequirements.json
水利标准.md 或 法律法规.mdpython scripts/build_reference_index.pyreferences_index.json
一键脚本（推荐）：不想记两条命令，用 scripts/maintain.py 一条搞定，且只重建改过的项（按 .md 修改时间判断）；拿不准是否漏跑时用 --check 一查便知；重建后条目数若较旧值腰斩会自动告警（多半是 .md 表格格式被破坏）。

python scripts/maintain.py --force     # 强制重建全部
python scripts/maintain.py --check     # 只检查是否漏重建（退出码 0=最新 1=需重建）

10.3 为什么"维护"有实际收益：版本过期检测

deterministic_checks.py 按"前缀+号、忽略年份"（如 SL252）建索引。所以只要清单里始终保持最新版，任何报告引用旧版都会被自动识别并标红，同时告诉你现行版是哪个——清单一更新，后续所有报告的旧版引用立即被检出。这正是"维护有效版本清单"的核心价值，而不只是记台账。

标准与法规的匹配差异：标准按"编号+年份"匹配，有版本过期检测（year_mismatch）；法规按名称匹配（deterministic_checks.py 引用检查段），无年份过期检测。因此法规清单的维护重点是保证名称与编号准确，而非靠年份自动识别新旧。

10.4 检查要求维护（检查要求.md）

增、删、改 42 条中的任意条目（如新增一条检查关注点、调整某条判定口径）→ 跑 parse_requirements.py。下次合成就按新要求逐条校审，报告中的"要求"原文、条目数、KPI 统计会自动跟着变。

10.5 可持续维护要点

  1. 改 .md，别碰 .json——见 10.1 的警告。requirements.json 虽可手改且立即生效，但与 .md 脱钩，日后重建会被覆盖，不建议作为常规维护方式。
  2. 重建后旧报告不会自动重审。requirements.json / references_index.json 只影响下次校审；已生成的报告要按新规则复评，需重跑"抽取 → 确定性检查 → 语义检查 → 合成"。
  3. 把 references/ 纳入版本管理。当前目录非 git 仓库，建议 git init 或定期备份 .md——这样维护历史可追溯（谁、何时、把哪条标准从哪版更新到哪版），误改也能回退。
  4. 清单只存"现行有效版"。表结构无"被替代旧版"字段，惯例是清单只保留当前有效版；旧版不留在清单里，自然被判 not_in_list / year_mismatch。若需记录替代关系作审计，可加一列 备注 手填，脚本不读该列、不影响。

12 常见问题与边界

Q1 · 默认输出什么格式？怎么改成 Markdown？

默认输出仪表板式 HTML，保存到输入文档同目录：<文档名>_校审报告.html。需要 Markdown 时在对话中明确说"输出 Markdown"，或手动运行 assemble_report.py --format=md。--format=both 可同时输出两种。

Q2 · 报告里 "第N页" 的定位是怎么来的？

抽取阶段为每段生成段落序号（P0123）。若运行了 page_map.py（需 Windows + Word），段落号会映射为 Word 页码（P0154→第16页）；未运行则回退为章节标题定位（如「3.6.3.3 §」）。表号定位形如「表3.7.2.2」。

Q3 · 某条被判"不适用"是什么意思？

表示该要求不适用于本文档（如内陆项目无潮位资料、未做分期设计洪水等），报告会说明不适用原因。这是正常结论，不代表漏查。

Q4 · 强制性条文（mp_*）怎么算"符合"？

以正文是否对该环节做了分析/论证为准，并给出定位。不得仅因提及规范名即判符合——必须看到实质的分析检查内容。

Q5 · 引用清单里标 not_in_list 的标准是错的吗？

不一定。引用清单为"现行有效版本"参考，not_in_list 可能是地方/行业外标准或内部技术文件。subagent 会区分"编号错误/已废止"与"非本清单范围但合理"两种情况。

Q6 · 表格统计值核算准吗？会不会误报？

对易误报场景（kW/台双单位、经验频率列、序号列、多合计行、区间值）只给 info，不直接判错，由 B 组 subagent 结合网格复核后判定。原则是"宁可漏报也不误报"。

Q7 · 大文件会卡吗？

抽取与确定性检查为单进程秒级。语义检查按类别并行，墙钟≈最慢一组；subagent 用 Grep 定位关键词后再分段 Read，不会整文件灌入。

Q8 · 怎么换用其他行业/版本的检查规则？

替换 references/ 下的清单文件（检查要求.md / 水利标准.md / 法律法规.md），重新运行 build_reference_index.py 与 parse_requirements.py 重建索引即可，流程其余部分不变。

日常的增删改、版本更新等持续维护，见 十一、清单动态维护。

效率建议：若环境不支持并发，可按 A→D 顺序逐组串行运行语义检查，结果不变，仅耗时变长。
